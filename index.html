Case study: tuning a Kubernetes messaging platform for EY

DigiGST 2.0 is EY's GST compliance platform. Its message queue runs Apache Pulsar on Azure Kubernetes Service, and it had to pass EY's load tests before go-live.

EY, DigiGST 2.0

From timeouts under load to 820 transactions a second with zero errors

Early stress tests failed well before the target load. New pods started when traffic rose, but they received no requests, and the consumer API timed out on every call.

  1. Found the cause. Pod CPU requests were set so high that the scheduler could not place new pods, so autoscaling had no effect.
  2. Fixed it. Right-sized CPU and memory requests. Traffic spread across the new pods and consumer API failures fell from 100% to zero.
  3. Found the next limit. Grafana showed the node itself at full CPU, because Pulsar and the application shared one node pool.
  4. Planned the next step. Proposed dedicated AKS node pools for each workload to reach the 5,000 TPS target.
